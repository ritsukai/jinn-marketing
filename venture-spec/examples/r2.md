# Rule 2: Always Cite Sources for Technical Claims

## Context

Marketing content about Jinn's technical capabilities must be accurate and verifiable. Developers (the target audience) verify claims by checking sources. Uncited technical claims damage credibility, and AI agents may hallucinate or misunderstand details. Citations provide trust and allow readers to dive deeper.

## Test Cases

### Case 1: Feature claims without sources

#### ❌ Violates Rule

**Tweet:**
```
Jinn supports autonomous multi-agent coding with intelligent task delegation and context-aware code generation!
```

**Why this is a violation:**
- Makes specific technical claims (multi-agent, task delegation, context-aware generation)
- No links to documentation or code
- Readers cannot verify claims
- Agent may have misunderstood or hallucinated capabilities

**Impact:** Skeptical developers dismiss as marketing hype. Lost credibility.

#### ✅ Follows Rule

**Tweet:**
```
Jinn supports autonomous multi-agent coding with git lineage context delegation [1].

Each agent works on its own branch, enabling parallel workstreams that PR back to parents [2].

[1] https://docs.jinn.dev/git-lineage
[2] https://github.com/jinn/jinn-gemini/blob/main/docs/architecture.md
```

**Why this follows the rule:**
- Same technical claims, but cited
- Readers can verify by following links
- Links to official documentation and code
- Builds trust through transparency

### Case 2: Performance claims without benchmarks

#### ❌ Violates Rule

**Blog post excerpt:**
```
Jinn is significantly faster than traditional coding assistants,
processing thousands of requests per hour with minimal latency.
```

**Why this is a violation:**
- Makes performance claims ("significantly faster," "thousands of requests")
- No link to benchmarks, tests, or comparative data
- Readers cannot verify the claim
- May be inaccurate or exaggerated

#### ✅ Follows Rule

**Blog post excerpt:**
```
In our benchmarks, Jinn processed 1,200 autonomous coding requests per hour
on a single instance [1], compared to 300 req/hour for Baseline Assistant [2].

Median response time: 2.3 seconds [3].

[1] https://github.com/jinn/jinn-gemini/blob/main/benchmarks/throughput-test.md
[2] https://baseline-assistant-docs.com/benchmarks
[3] https://github.com/jinn/jinn-gemini/blob/main/benchmarks/latency-results.json
```

**Why this follows the rule:**
- Specific numbers with citations
- Links to benchmark methodology and raw data
- Comparative claim cites competitor's public benchmarks
- Fully verifiable by readers

## What Requires Citations

### ✅ Always Cite

- **Feature claims:** "Jinn supports X" → link to docs/code
- **Performance claims:** "Jinn processes Y requests/hour" → link to benchmarks
- **Architecture descriptions:** "Jinn uses git lineage" → link to architecture docs
- **Comparisons:** "Faster than X" → link to comparative data
- **Technical examples:** "Here's how to use feature Z" → link to code example or demo
- **Roadmap items:** "Coming soon: feature W" → link to roadmap or GitHub issue

### ⚠️ Rarely Needs Citation (but still good practice)

- **General concepts:** "Multi-agent systems enable parallel work" (common knowledge)
- **User testimonials:** "User X said Y" (if directly quoted and attributed)
- **Marketing copy:** "Jinn makes coding easier" (subjective value prop, not technical claim)

### ❌ Never Claim Without Citation

- Specific technical capabilities
- Performance or benchmark data
- Architectural details
- Comparisons to competitors
- Code examples or usage patterns

## How to Cite Effectively

### 1. Inline Citations (Preferred for Short Content)

**Example:**
```
Jinn's git lineage context (https://docs.jinn.dev/git-lineage)
enables agents to inherit historical context when delegating work.
```

### 2. Footnote Citations (Preferred for Long Content)

**Example:**
```
Jinn's git lineage context [1] enables agents to inherit historical
context when delegating work [2].

[1] https://docs.jinn.dev/git-lineage
[2] https://github.com/jinn/jinn-gemini/blob/main/docs/delegation.md
```

### 3. Link Anchors (Preferred for Visual/Video Content)

**Example (video description):**
```
See git lineage in action: https://docs.jinn.dev/git-lineage
Full code example: https://github.com/jinn/jinn-gemini/tree/main/examples/delegation
```

## What to Do When Documentation Doesn't Exist

**Scenario:** You want to make a technical claim, but there's no documentation or code to cite.

**Options:**

1. **Create the documentation first:**
   - Write a brief explainer in the Jinn docs
   - Submit as PR to core team
   - Once merged, cite the new documentation

2. **Request documentation from core team:**
   - Use core team coordination protocol (db8)
   - Request: "Need documentation for feature X to support marketing content"
   - Wait for docs, then publish marketing content

3. **Link to code directly:**
   - If docs don't exist but code does, link to the implementation
   - Example: "Feature X is implemented here: [link to code]"
   - Better than no citation

4. **Don't make the claim:**
   - If no documentation or code exists, the feature may not be shipped
   - Don't claim unshipped features without labeling them as "roadmap" or "coming soon"
   - Cite the roadmap issue instead

## Enforcement Checklist

Before publishing content with technical claims:

- [ ] Identify all technical claims in the content
- [ ] For each claim, verify it's accurate (check docs, code, or with core team)
- [ ] Add inline citations or footnotes for each claim
- [ ] Verify citation links work and point to the right section
- [ ] If documentation doesn't exist, create it or request it

**If any checkbox is unchecked for a technical claim, do not publish until cited.**

## Real-World Impact

### Example: Uncited Claim Backfires

**Scenario:** Agent tweets "Jinn can autonomously fix bugs in production code" without citation.

**Reader response:** "Interesting! Can you share docs or examples?"

**Problem:** Feature doesn't actually exist (agent hallucinated). Now must either:
- Admit error (damages credibility)
- Ignore question (damages credibility)
- Scramble to build feature (wastes core team time)

**Outcome:** Lost trust, wasted effort.

### Example: Cited Claim Builds Trust

**Scenario:** Agent tweets "Jinn's code spec enables consistent AI-generated codebases [link to spec]"

**Reader response:** "Wow, this is well thought out. I checked the spec—impressive."

**Outcome:** Reader explores docs, stars GitHub repo, shares with colleagues. Trust built through transparency.

---

## Application to AI Agents

When drafting content:

1. **Identify technical claims** in your draft
2. **Verify accuracy** by reading docs or code
3. **Add citations** inline or as footnotes
4. **If no docs exist**, create them or request them
5. **Double-check links** before publishing

**The rule is absolute:** Technical claims require citations.
